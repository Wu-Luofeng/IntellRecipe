# 订单模块测试报告（订单设计评估）

> 目标：验证订单主链路与边界设计，找出设计与实现层面的不足。
> 环境：本地微服务（user/item/voucher/gateway）+ 本地 Nacos + RabbitMQ/MySQL/Redis（SSH 隧道连云端），网关 `127.0.0.1:10010`。
> 测试账号：13800138000（主）/ 13812345001（越权验证）；测试产生的订单为演示数据。

## 1. 通过用例（执行结果）

| # | 用例 | 步骤 | 结果 |
|---|---|---|---|
| P1 | 整单模型（不拆单） | 商家6+商家5 各 1 件一次结算 | ✅ 仅生成 1 个订单（20260903000008），明细 2 条且分属两家 |
| P2 | 异步受理→MQ→完成 | create 立即返回订单号→数秒后 | ✅ 受理后 status=4，消费后 status=0，购物车对应商品被清空 |
| P3 | 支付即完成/时间线 | pay 后查详情 | ✅ status=2，状态日志含 4→0→1→2 四步 |
| P4 | 券抵扣 | 用券下单 | ✅ total/discount/pay 正确，券核销，池中券减一 |
| P5 | 取消自动退券 | 用券单取消 | ✅ status=3，券退回（usable 恢复） |
| P6 | 已核销券再下单 | 用同一张已用券 | ✅ 受理 precheck 同步拦截 |
| P7 | 并发抢同一张券 | 两单同时用一张券 | ✅ 一单成功，另一单异步核销失败→status=5+failReason（幂等防超发） |
| P8 | 越权访问 | 用户B 查用户A 订单详情 | ✅ 拒绝（success=false） |
| P9 | 支付幂等 | 对已完成订单再次 pay | ✅ 拒绝“订单状态不允许支付” |
| P10 | 取消限制 | 已支付订单 cancel | ✅ 拒绝“仅待支付订单可以取消” |
| P11 | 参数校验 | 缺收货电话下单 | ✅ 拒绝“请填写完整…” |
| P12 | 空勾选 | 全不勾选后下单 | ✅ 拒绝“没有可结算的商品” |
| P13 | 多商家券门槛 | 整单跨商家、券只抵所属商家小计 | ✅（voucher_merchant_id 按商家小计计算） |

## 2. 发现的设计不足（重要）

| # | 问题 | 复现/现象 | 建议 |
|---|---|---|---|
| **D1** | **下单无防重** | 同一购物车**连续两次提交 → 成功生成 2 笔订单**（20260904000001/…002，均为 status=0），同一批商品被“双份购买” | 前端提交按钮置灰防连点（已有 submitting，需补充到两处入口）；**后端增加幂等键**：`CreateOrderDTO.clientToken`，受理时以 (userId, clientToken) 防重（唯一索引或 Redis SETNX），重复提交直接返回原订单号 |
| D2 | 待支付订单**无超时自动关闭** | 只实现了“处理中→失败”的补偿定时任务；`status=0 待支付`长期不支付不会自动取消/释放券 | 增加“待支付超时(如30min)自动取消并退券”的 @Scheduled 任务，避免积压与券长时间被占 |
| D3 | 网关限流返回非业务结构 | 连续调用偶发 HTTP 429（乱码提示），前端无法按 Result 处理 | 网关/限流器返回统一 JSON（success=false + 文案），或提示由前端兜底“操作太频繁” |
| D4 | 订单号 6 位序列按日取模 | 极端情况下同日超过 1,000,000 单会与既有号冲突（当前有 DB 唯一索引兜底，但冲突无“重试生成”逻辑，用户会看到一次失败） | 冲突捕获后重试生成或扩大位数/改为 Redis INCR 不截断 |
| D5 | status=5 失败单缺少用户可见的补救 | 失败原因仅存 failReason、无管理端列表/人工处理入口 | 可加管理端“失败订单”查看/重试，便于课程演示与排障 |
| D6 | 补偿可靠性依赖单实例 | OrderCompensateTask 为本地 @Scheduled；若 item 多实例部署需加分布式锁 | 当前单实例场景可接受，多实例需引入分布式锁（Redis） |

## 3. 结论

订单模块的核心设计（整单一单 + 状态机可追溯 + MQ 异步受理/手动 ACK + 本地留痕补偿 + 券原子幂等 + 越权与状态约束）经测试表现稳定，边界拦截到位。
主要设计短板集中在 **D1 下单防重缺失**（会造成重复订单，属于必须修复项）与 **D2 待支付超时未自动关单**（属于重要业务补强项）。建议按上表优先级修复 D1→D2→D3，其余作为增强项跟踪。
